# M1 自习座位预约模块需求规格说明书 V0.1

**项目名称：** 校园资源服务平台  
**模块：** M1 — 个人自习座位预约  
**版本：** V0.1  
**状态：** 需求评审稿  
**适用阶段：** 第一次功能迭代  
**关联模块：** D（公共资源与身份）、M2（整教室预约）、M3（维修管理）

---

# 一、模块目标与边界

## 1.1 业务目标

M1 为学生提供自习教室浏览、座位查询、时间轴查看、座位预约、签到、取消、提前结束和违约管理功能。

系统自动处理个人座位预约，不设置人工审批环节。

第一次迭代应实现完整的个人预约闭环，并与 D 的统一资源占用能力集成。

## 1.2 职责划分

**M1 负责：**

- 个人座位预约的资格和时间规则。
- 预约记录的创建、查询、取消。
- 签到、超时未签到和违约处理。
- 签到后的提前结束与自然完成。
- 个人预约状态管理及页面展示。
- 对 D 返回的占用信息形成座位时间轴。
- 处理 D 通知的紧急维修导致的个人预约取消。

**D 负责：**

- 统一用户身份认证和权限识别。
- 教室与座位主数据。
- 统一资源可用性查询。
- 个人座位、整间教室的原子占用与释放。
- 不同来源的资源冲突检查与记录。
- 紧急停用时的跨模块冲突处理协调。

**M2 负责：**

- 整间教室申请、用途与优先级。
- 两级人工审批。
- 整室预约状态及被系统取消后的业务处理。

**M3 负责：**

- 报修、紧急程度及影响范围确认。
- 维修派单、维修进度和验收。
- 发起整室紧急停用或计划施工限制。
- 确认符合恢复使用条件后请求解除限制。

M1 不负责教室预约审批和维修安全判断。

# 二、用户角色与访问控制

## M1-R01 用户登录

预约、取消、签到和提前结束必须在登录后执行。

M1 从 D 的可信认证信息中获取当前用户 ID。

## M1-R02 无人工审批

学生提交预约后，系统自动校验预约规则和资源冲突，成功则立即确认。

M1 不设置人工审批管理员和待审批状态。

## M1-R03 个人预约隐私

学生只能查看自己的预约记录和状态。

学生不能查看其他学生的预约 ID、身份信息或预约详情，也不能取消、签到或提前结束其他人的预约。

公共座位时间轴仅展示占用时段和原因，不暴露预约人身份。

# 三、前端查询与时间轴

## M1-F01 选择自习教室

学生首先进入教室选择页面。

展示可用于个人预约的教室名称、位置、座位数量和开放时间。

点击某间教室后，进入该教室的座位选择页面。

## M1-F02 选择座位

座位页面展示该教室的座位编号及基础属性。

第一版使用规则网格展示，不要求精确的教室平面图。

学生点击座位后查看该座位在指定日期的可视化时间轴。

## M1-F03 可视化时间轴

时间轴覆盖每日 07:00～22:00，以 30 分钟为最小展示刻度。

**主色定义：**

| 颜色 | 类型 | 是否阻止预约 |
|---|---|---|
| 白色 | 空闲 | 否 |
| 蓝色 | 有效个人座位预约 | 是 |
| 黄色 | M2 已批准整室预约 | 是 |
| 红色 | M3 整室停用限制 | 是 |

**普通维修提示：**

不影响教室正常使用的 M3 维修工单，只通过提示标记或独立信息层展示，不占用时间轴的主色，也不影响预约。

**整室同步展示：**

当某教室存在有效 M2 整室占用或 M3 停用限制时，该教室所有座位在对应时段必须显示相应的占用状态。

**占用原因：**

点击占用时间段时，可以查看原因，例如“已被预约”“整教室活动”“维修停用”，但不展示其他学生信息。

**颜色优先级：**

如果因异常处理、历史数据或临时状态存在多种重叠原因，时间轴主色建议按照“紧急维修红色 ＞ 整室预约黄色 ＞ 个人预约蓝色”绘制，并保留全部原因供查看。

颜色只是展示规则，不得代替后端资源冲突判断。

## M1-F04 选择时间段

学生可以从可预约时间轴上选择预约开始和结束时间。

系统展示时长并校验预约是否合法。

前端校验仅用于交互提示，提交后必须由后端重新校验。

# 四、预约业务规则

## M1-R04 开放时间

自习教室每日 07:00～22:00 开放。

预约开始时间不早于 07:00，结束时间不晚于 22:00。

不支持跨自然日预约。

## M1-R05 预约开放窗口

仅允许从使用日期前一天 22:00 开始预约。

使用当天可预约尚未开始的时段。

不允许预约已经开始的时段，也不允许提前超过一天预约。

所有时间判断使用统一的校园本地时区。

## M1-R06 单次预约时长

单次预约最短 1 小时，最长 4 小时。

## M1-R07 时间粒度

预约开始和结束时间均为整点或半点，例如 09:00、09:30、10:00。

不允许 09:15 等非半小时边界。

## M1-R08 用户预约数量与重叠

不限制单个用户的预约总条数。

但同一用户不得持有时间重叠的多个有效座位预约，即使这些预约属于不同座位或不同教室。

## M1-R09 预约冲突

以下情况禁止创建新预约：

1. 目标座位在该时段存在其他有效个人预约。
2. 当前用户已有重叠的有效座位预约。
3. 所属教室存在重叠的有效 M2 整室占用。
4. 所属教室存在重叠的 M3 整室停用限制。
5. 座位或教室处于长期禁用状态。
6. 用户因当月违约次数达到限制而无预约资格。

普通且不影响使用的维修工单不构成冲突。

时间区间采用左闭右开表示，例如 `[09:00, 11:00)`。

## M1-R10 自动创建预约

用户提交后，M1 检查个人预约规则，并通过 D 原子地建立资源占用。

占用和业务预约记录必须保持一致。

并发情况下，同一座位同一重叠时段至多允许一个有效预约成功。

创建成功后状态为 `RESERVED`。

# 五、取消、签到与提前结束

## M1-R11 预约开始前取消

用户可以在距离预约开始时间不少于 30 分钟时，主动取消本人未开始的预约。

例如预约 09:00 开始：

- 08:29 可以取消。
- 08:30 可以取消。
- 08:31 不允许按预约开始前取消规则操作。

取消成功后，状态变为 `CANCELLED`，释放对应占用，不记录违约。

## M1-R12 签到时间窗口

学生只能在预约开始前 15 分钟至开始后 30 分钟内签到，两个边界均包含在内。

例如预约开始时间 09:00，则允许签到时间为 08:45～09:30。

仅预约本人能够签到。

签到成功后状态变为 `CHECKED_IN`，记录实际签到时间。

## M1-R13 签到后提前结束

学生成功签到后，只有到达原计划预约开始时间，才能操作“提前结束”。

提前结束视为正常完成，不计违约。

例如原预约为 09:00～13:00，学生在 09:05 签到、11:00 提前结束：

- 历史记录保留原预约时段 09:00～13:00。
- 记录实际结束时间 11:00。
- 将 11:00～13:00 释放给后续预约。
- 预约状态更新为 `EARLY_FINISHED`。

如用户在 08:50 提前签到，应等到 09:00 后才可以执行提前结束操作。

## M1-R14 未签到违约

如果学生在预约开始后 30 分钟内未完成签到，系统自动：

1. 将预约状态改为 `NO_SHOW`。
2. 释放剩余座位占用。
3. 记录一次未签到违约。
4. 保留预约历史供本人查询。

09:00 开始的预约，09:30:00 仍允许签到，超过 09:30:00 才符合违约处理条件。

签到和超时任务必须采用一致的时间判定及并发控制，避免同时产生签到成功与违约状态。

## M1-R15 月度违约限制

学生在同一个自然月内累计出现 3 次 `NO_SHOW`，当月不得再创建新的个人预约。

**已经成功创建的有效预约继续保留。**

进入下一个自然月后，当月违约计数重新开始，但历史记录保留。

违约月份以预约的计划开始日期所属月份为准，避免定时任务延迟执行造成跨月计数错误。

由于 M3 紧急维修导致的系统取消不得计入违约。

## M1-R16 自动完成

成功签到、未提前结束且未被系统取消的预约，在其计划结束时间到达后自动进入 `COMPLETED`。

学生不需要主动签退。

# 六、M2、M3 跨模块联动

## M1-R17 M2 整室占用

M2 的申请只有在审批完成且 D 成功建立整室占用后，才算正式生效。

M1 在对应时间段禁止所有所属座位的新预约，并在时间轴上显示黄色。

正常 M2 申请不得覆盖已有效确认且时间冲突的个人座位预约。

## M1-R18 M3 普通维修

若 M3 确认维修不影响教室正常使用：

- 不创建阻止预约的资源限制。
- 不取消现有 M1/M2 预约。
- 不阻止新增 M1/M2 预约。
- 在时间轴上展示维修提示。

## M1-R19 M3 整室停用

若 M3 确认教室必须停止使用，D 应根据安全停用起点建立整室限制。

对于必须立即停用的安全故障，停用从确认或实际发现必须停用的时刻生效，不等待维修人员到场。

对需要在未来施工时段关闭教室、且此前仍可安全使用的维修，按经确认的施工时段建立限制。

## M1-R20 紧急维修冲突处理

当整室安全停用与已经存在的 M1 或 M2 有效预约发生冲突时：

1. D 识别受影响的预约。
2. 系统禁止新建冲突预约。
3. M1 将受影响的个人预约标记为 `CANCELLED_BY_SYSTEM`。
4. M2 将受影响的整室预约标记为其对应的系统取消状态。
5. 系统生成通知，告知受影响预约人，并说明取消原因。
6. 相关业务记录和操作历史保留。
7. M3 维修结束且完成必要验收后，按安全恢复规则解除停用限制。

如果维修仅与某条个人预约的部分时间重叠，**取消整条个人预约**，不对它进行自动拆分或部分保留。

系统取消不记录学生违约。

**场景 A：维修在讲座前完成**

若教室在讲座开始前已恢复安全，并且停用时段不与讲座重叠，讲座可以保留。

**场景 B：维修与讲座时间重叠**

若整室必须停用的时间与讲座重叠，应取消讲座，通知申请人另选教室。

**场景 C：维修计划在讲座之后，但教室当前已不安全**

从必须停用的时间起，直至具备安全恢复条件之前，教室不可使用。

期间受影响的讲座和个人预约应取消，不应等到维修开始时才处理。

## M1-R21 资源释放与历史保留

系统对外应保证：紧急停用生效后，教室不会同时保持可履行的冲突预约。

即使冲突预约已被取消，也应保留取消记录、来源信息和审计信息，以便追溯和重试。

解除 M3 维修限制仅表示该项停用原因解除，不得恢复先前已取消的预约。

取消的预约不会因维修完成而自动复活，预约人需要重新申请。

# 七、预约状态机

| 状态 | 含义 | 典型触发条件 |
|---|---|---|
| `RESERVED` | 已预约，未签到 | 预约成功 |
| `CHECKED_IN` | 已签到 | 签到成功 |
| `COMPLETED` | 正常结束 | 到达预约结束时间 |
| `CANCELLED` | 主动取消 | 开始至少 30 分钟前取消 |
| `EARLY_FINISHED` | 正常提前结束 | 签到后、开始时间起主动结束 |
| `NO_SHOW` | 未签到违约 | 超过签到截止时间 |
| `CANCELLED_BY_SYSTEM` | 系统取消 | 紧急维修等不可履行情况 |

正常转移：

- `RESERVED → CHECKED_IN → COMPLETED`
- `RESERVED → CHECKED_IN → EARLY_FINISHED`
- `RESERVED → CANCELLED`
- `RESERVED → NO_SHOW`
- `RESERVED / CHECKED_IN → CANCELLED_BY_SYSTEM`

终态不得无理由恢复为有效预约。

# 八、非功能性需求

## M1-N01 数据一致性

预约记录与 D 的资源占用应具有明确的事务或一致性保障。

创建、释放和紧急停用操作必须具备并发保护与必要的幂等性。

## M1-N02 安全与隐私

所有用户操作依据后端认证身份授权。

其他学生不可读取个人预约详情，不可通过修改 ID 越权操作。

时间轴不返回预约人个人信息。

## M1-N03 可测试性

预约时间规则、签到截止、月底违约限制、紧急维修等必须使用可控时钟进行自动化测试。

## M1-N04 可追溯性

记录预约创建、取消、签到、违约、提前结束和系统取消的重要操作时间与原因。

## M1-N05 统一时间

业务规则按照学校所在地约定的校园时区处理。

数据库建议存储带时区的时间戳，业务日期计算时明确转换至校园本地时区。

# 九、第一次迭代交付内容

第一轮交付以下最小可操作闭环：

1. 教室选择、座位选择、可视化时间轴。
2. 30 分钟粒度时间选择，1～4 小时预约。
3. 自动校验预约窗口、开放时间、并发占用。
4. 登录身份关联的预约创建与个人记录查询。
5. 开始前取消。
6. 签到及 30 分钟超时违约。
7. 签到后提前结束及剩余时段释放。
8. 自动完成。
9. 当月 3 次违约限制新增预约。
10. M2 占用、M3 停用与普通维修提示的时间轴展示。
11. 紧急维修取消受影响预约且不记违约。
12. 关键自动化测试及 PostgreSQL 持久化。

**本轮不实现：**

- M1 人工审批。
- 单座位维修限制。
- 自动推荐替代座位或教室。
- 预约动态二维码、复杂通知渠道。
- 复杂管理员管理后台。
- 自动拆分部分时间冲突的预约。

# 十、风险识别与应对方案

| 编号 | 风险 | 可能后果 | 建议控制措施 |
|---|---|---|---|
| RISK-01 | 两人同时预约同一座位 | 重复占用 | PostgreSQL 事务、排斥约束或统一加锁策略 |
| RISK-02 | 学生预约与 M2 整室批准并发发生 | 整室与单座位重复分配 | 所有占用走 D 的统一原子检查与创建 |
| RISK-03 | 紧急维修发生时已有 M1/M2 预约 | 不安全使用、已有活动临时中断 | 优先封闭资源，识别并取消冲突预约，通知用户 |
| RISK-04 | 紧急停用与取消预约之间的处理失败 | 资源已停用但预约状态未同步 | 以停用为安全优先，使用可重试的取消任务、状态核对和审计记录 |
| RISK-05 | 维修解除误恢复其他占用 | 非法重新开放或恢复旧预约 | 按来源解除限制，旧预约不自动恢复 |
| RISK-06 | 签到与超时任务同时运行 | 同时出现 CHECKED_IN 和 NO_SHOW | 以服务器时间及事务状态转移做原子判定 |
| RISK-07 | 半小时边界或 22:00 边界判断错误 | 非法预约或误拒合法预约 | 固定边界约定并进行参数化测试 |
| RISK-08 | 月度违约计数跨月错误 | 错误处罚学生 | 以预约开始日期所属校园自然月计算 |
| RISK-09 | 提前结束只修改状态，未释放占用 | 时间轴持续显示蓝色 | 记录实际结束时间并原子更新有效占用结束时间 |
| RISK-10 | 学生通过请求参数访问他人预约 | 隐私泄露、越权操作 | 后端身份检查、权限测试、最小必要返回字段 |
| RISK-11 | 普通维修提示覆盖了真实占用颜色 | 用户误判是否可约 | 占用主色与维修提示分层展示 |
| RISK-12 | 未来停用结束时间未知 | 错误地提前开放教室 | 使用持续有效的停用限制，完成安全确认后解除 |
| RISK-13 | D 公共层接口尚未稳定 | M1、M2、M3 集成延迟 | 先冻结 API 契约，提供测试替身及契约测试 |
| RISK-14 | 第一轮范围较大 | 前端、定时任务或联动无法全部完成 | 按预约主流程优先交付，尽早开展端到端测试 |

## 重点风险解释

### 10.1 安全停用必须优先于取消结果同步

紧急维修不能因为某个预约状态尚未成功更新，就继续允许教室使用。

系统应先确保资源从可预约性查询和新预约创建中被禁止使用，然后可靠地完成已有预约取消、通知和记录同步。

如果采用单 PostgreSQL 数据库，可优先通过统一事务提交停用和相关预约变更；如果跨独立服务，则必须有可重试的协调机制。

### 10.2 违约限制必须避免误罚

学生在允许签到的最后一刻签到成功，系统不得将其同时判定为违约。

系统取消、提前结束、主动合法取消均不算未签到违约。

### 10.3 预约时间轴不可暴露个人信息

即使所有学生能查看某座位何时被占用，也不代表可以查看是谁预约的。

时间轴仅返回展示所需的状态、时间和公开原因。

# 十二、需求验收标准

M1 V0.1 第一次迭代满足以下条件可视为通过验收：

- 学生能够通过真实页面完成预约、签到、取消及提前结束。
- 所有时间、时长、违约和权限规则由后端实施。
- D 能正确避免个人预约、整室使用和紧急维修的非法资源分配。
- 座位时间轴正确反映不同占用原因及普通维修提示。
- 系统能自动处理未签到、自然完成和紧急维修导致的预约取消。
- 系统取消不产生学生违约。
- 数据库记录、状态转换和实际可预约性一致。
- 关键业务测试通过，并保留可审查的测试结果。

**版本说明：** V0.1 已纳入用户确认的十二项 M1 需求、同一学生禁止重叠预约、第三次违约后保留既有预约、紧急维修整体取消冲突预约、预约开始后才可提前结束等规则。仍需在开发前确认具体跨模块 API 契约及通知职责。
