> 版本：V0.1

## 阅读说明：需求来源及本稿的设计选择

- **课程任务书直接要求**：M2 具备权限门槛、整教室申请提交、多级审批（通过／驳回）、超时自动撤销，并与 M1 的座位占用产生可追溯的联动。
- **与 M1 V0.4 对齐的已明确约定**：采用**两级人工审批**；D 负责资源主数据、角色权限、统一可用性与原子占用；**只有两级审批完成且 D 成功建立整室占用后，整室预约才生效**；普通整室申请不可覆盖已确认的个人座位占用；M3 的紧急安全停用优先于已有预约。
- **本稿为使 AI 能直接实现而提出、尚待项目组评审确认的规则**：申请最早/最晚时间、预约时长、审批时限、审批角色名称、接口路径、状态枚举、数据字段等。这些是**建议基线，不是课程任务书原文规定**。如与项目现有 D 契约或已通过的组内 ADR 冲突，以组内书面决策为准，并同步更新本文件。
- **实现原则**：首迭代优先交付可在 Web 页面、HTTP 接口和数据库中验证的完整闭环；不把复杂通知、消息队列、工作流引擎、电子签章等作为前置条件。

## 一、模块目标与边界

### 1.1 业务目标

M2 面向被授权的校园用户，提供整间教室的查询、预约申请、申请进度查询、申请撤销，以及两级审批人员的待办查看、通过和驳回操作。系统在审批成功后经由 D 原子建立整室占用，使对应时间段内该教室的**全部座位**不可再被 M1 预约；到期、拒绝、撤销及紧急维修时正确处理业务状态与占用。

完整流程为：

`选择教室与时间 → 提交申请 → 一级审批 → 二级审批 → D 原子确认整室占用 → 已批准 → 活动结束/合法撤销/紧急停用`

任一待审阶段都可能因驳回、申请人撤销或超时而终止。

### 1.2 职责划分

**M2 负责：**

- 检查整教室申请资格与本模块业务规则。
- 保存申请信息、用途、时间、申请状态及审批记录。
- 两级人工审批的权限校验、顺序控制、超时处理。
- 在终审通过后调用 D 建立整室占用，在取消或受影响终止时调用 D 释放**本申请对应**的占用。
- 处理 D 转发的维修紧急停用结果；保留处理原因及历史。
- 向申请人、审批人提供相应页面与接口；记录重要操作审计。

**D 负责（不在 M2 内重复实现）：**

- 统一认证、RBAC、当前用户组织/管理范围和教室访问权限。
- 教室主数据：教室编号、名称、建筑位置、容量、开放时间、资源可用状态、所属管理范围。
- 教室整体及座位的统一时间区间冲突判断、原子占用与按来源释放。
- M1 个人座位占用、M2 整室占用、M3 停用限制的来源追溯与统一可用性查询。
- 按统一规则对有效占用/停用提供可查询的时间轴数据。

**M1 负责：**

- 个人座位预约及座位时间轴显示；读取 D 返回的整室占用信息后，将对应座位时段标为黄色且拒绝个人预约。
- 维护 M1 自身业务记录；M2 不直接变更 M1 预约或座位表。

**M3 负责：**

- 故障等级、是否需要紧急整室停用及停用生效区间的业务判定。
- 向 D 建立、解除维修限制；由 D 协调通知受影响业务模块。

**权威边界**：M2 是“整室申请与审批业务状态”的权威；D 是“物理资源是否可以被占用”的权威。模块间通过已授权的公开 HTTP 接口交互，**严禁 M2 直接查询或修改 D、M1、M3 的内部业务表**。

### 1.3 首迭代原则

1. **先审后占**：待审不预先锁定教室；只有终审确认且 D 占用成功才对 M1 生效。
2. **逐级审核**：一级通过才能进入二级；一个人不能审批自己的申请，也不能同时充当同一申请的两级审批人。
3. **权限后端校验**：按钮是否显示不能代替接口授权。
4. **冲突以 D 为准**：前端可预检，但提交与终审均重新校验；并发最终由 D 原子决定。
5. **可追溯、可恢复**：所有审批、超时、撤销及跨模块占用操作保留原因和唯一关联标识；D 结果不明确时不得误报成功。
6. **控制范围**：普通定时任务处理超时；不强制引入独立工作流引擎或消息队列。

## 二、用户角色与权限控制

### M2-R01 登录与可信身份

所有教室查询、申请、本人记录和审批操作均要求登录。M2 使用 D 返回的可信用户标识、角色和资源范围，不接受请求体中的 `applicantId`、`reviewerId` 作为实际操作者。

未登录返回 `401`；已登录但无权限返回 `403`。不得通过变更前端传参查看或操作不属于自己的申请。

### M2-R02 角色门槛

建议由 D 配置以下权限（名称可随现有 RBAC 契约映射）：

| 权限标识（建议） | 允许操作 | 范围限制 |
| --- | --- | --- |
| `M2_APPLY` | 查询可申请教室、提交整室申请、查看/撤销本人申请 | 仅允许申请 D 授权范围内的教室 |
| `M2_APPROVE_L1` | 一级审批、查询本级待办 | 仅允许审核所属院系/区域等被授权范围 |
| `M2_APPROVE_L2` | 二级审批、查询本级待办 | 仅允许审核被授权的校级/终审范围 |
| `M2_AUDIT_READ`（可选） | 查看指定范围内的完整流转记录 | 只读，不自动具有审批权限 |

普通学生不因具有 M1 预约权限就自动具有 `M2_APPLY`。管理员身份也不自动绕过审批，除非 D 另行明确授权并形成决策记录。

### M2-R03 审批隔离

- 一级与二级审批均由真实授权用户点击完成，不允许服务端自动“模拟通过”。
- 审批人不能审批本人提交的申请。
- 同一人不得完成同一申请的一级与二级审批，即使同时拥有两种角色。
- 当前申请必须处于该审批人对应的待审批阶段；不得越级、补批或重复改变已定结果。
- 审批接口应检查用户在**本次操作发生时**仍具有对应权限和教室范围。

### M2-R04 数据可见性

- 申请人只能查看、撤销本人申请。
- 审批人员只查看其权限范围内的待办与已处理记录。
- 对普通浏览用户，教室占用仅展示“整教室活动/不可预约”等必要信息，不公开申请人身份、联系方式、完整用途或审批意见。
- 申请人的用途与驳回原因只向申请人、已授权审批人及审计人员展示。

## 三、教室查询与申请表单

### M2-F01 选择教室

展示当前用户有权申请且支持整室预约的教室，至少包含：教室名称/编号、所在楼宇/区域、可容纳人数、开放时间和可用状态。支持按楼宇/区域筛选。

教室及其座位、开放时间、长期禁用等主数据从 D 获取；M2 不建立一份可自行更改的教室主数据。

### M2-F02 查询时段可用性

用户选择使用日期及起止时刻，页面展示该教室是否存在下列阻断来源：

- M1 有效的个人座位占用（哪怕只有一个座位被占用，也阻止整室占用）。
- 已生效的 M2 整室占用。
- M3 有效的整室停用限制。
- D 判定的教室长期禁用或不开放。

查询可用只是**快照**，不代表已预留。若查询失败，应显示“查询失败/重试”，**不得显示为空闲**。其他申请处于审核中但尚未产生实际占用时，不阻止查询结果显示空闲；页面可加“最终以审批通过时再次确认的可用性为准”的提示。

### M2-F03 提交申请

表单至少包含：教室、预约开始时间、结束时间、用途、预计参与人数。申请人身份由服务端获取。

- 用途为非空字符串，去除首尾空白后长度 `5～200` 个字符（**本稿建议值**）。
- 预计人数为 `1` 至 D 返回的教室容量，不能为小数；容量未知时不得跳过人数校验并默许申请成功。
- 前端显示申请时长及审批说明；提交中禁用重复点击，后端仍使用幂等键防重。
- 申请创建成功只表示**已提交审核**，不得提示“教室预约成功/已经占用”。

### M2-F04 我的申请

申请人可分页查询本人全部申请，支持按日期和状态筛选；列表至少展示教室、用途摘要、计划时段、申请时间、当前状态和当前审批环节。

申请详情展示两级审批记录、处理时间、审批意见、最终结果、撤销或超时原因；对结果尚未确认的情况展示“处理中”，不伪装为成功。

### M2-F05 审批工作台

一级和二级审批人分别查看本级待办；每条展示教室、时段、用途、申请人必要身份信息、人数、提交时间和当前审批截止时刻。

审批人可点击“通过”或“驳回”。驳回必须填写 `2～200` 字符的原因（**建议值**）；通过可选填写简短意见。审批结果提交后刷新详情，若已被他人处理或超时，给出明确提示。

### M2-F06 申请撤销

申请人在“我的申请”中撤销符合条件的申请。确认弹窗说明：待审批撤销立即终止流程；已批准且尚未开始的申请撤销将释放对应整室占用。撤销成功后不可恢复原申请，可重新提交新申请。

## 四、整教室申请业务规则

> **配置说明**：本节时间范围是为了让首迭代可开发、可测而选取的建议规则，课程任务书**未规定 M2 的具体提前天数、时长上限和审批小时数**。请项目组确认后将其作为 M2 需求基线；不要直接照搬 M1 的“每人每天 4 小时”额度规则。

### M2-R05 时间标准与区间

- 使用校园本地时区 `Asia/Shanghai`；服务端时间权威，数据库按团队统一时间存储规范处理并明确转换。
- 时间段采用左闭右开 `[startAt, endAt)`；当且仅当 `start1 < end2 && start2 < end1` 时区间重叠。
- 不接受跨自然日、`endAt <= startAt`、无时区歧义无法解析的时间。
- 起止时刻须位于整点或半点，秒和更小单位必须为零；例如 `09:00～10:30` 合法，`09:15～10:15` 非法。
- 建议整室可申请时段 `07:00～22:00`，并同时受 D 返回的教室开放时间限制；两者取交集。特殊时段若需开放，先变更经评审的配置而不是绕过后端校验。

### M2-R06 申请时间窗口（建议基线）

- 申请时计划开始时间须**至少晚于或等于当前服务端时间 2 小时**。
- 最早可提前 **14 个自然日**提交，不允许更远期；以提交时刻到计划开始时刻判断，建议精确为 `startAt <= now + 14 days`。
- 单次申请最短 **1 小时**、最长 **8 小时**，上下限均包含。
- 以上是 M2 特有规则，与 M1 的前一晚 22:00 开放、单次最多 4 小时、每日 4 小时额度互不混用。

### M2-R07 申请前资格校验

创建申请之前，后端至少核验：

1. 用户具有 `M2_APPLY` 且可访问/申请该教室。
2. 教室在 D 主数据中存在，支持整室申请，且未长期禁用。
3. 时间满足 R05、R06，以及该教室的实际开放时间。
4. 用途和预计人数符合 F03。
5. D 当前可用性检查未发现阻断来源；D 查询失败则本次申请返回明确失败，不能把未知视为可用。

本次可用性预检不是占用操作；提交后到终审之间，M1 或其他 M2 可能合法占用该教室。预检通过后创建申请为 `PENDING_L1`，不调用 D 创建整室占用。

### M2-R08 幂等提交

客户端每次“创建申请”生成唯一 `requestId` 或 `Idempotency-Key`。同一申请人、同一请求标识的重复请求只能对应一条申请，并返回既有结果；同一标识携带不同表单内容则返回参数冲突，不得默默覆盖。

**不同请求标识**即使时间相同也可存在待审申请，第一版不强制禁止重复申请表单；但只允许与 D 实际有效占用无冲突的申请通过最终确认。

### M2-R09 一级审批

仅当状态为 `PENDING_L1`，且服务端当前时刻**严格早于**一级审批截止时刻时，授权一级审批人可操作。

- `APPROVE`：追加不可覆写的一级审批记录，将状态改为 `PENDING_L2`，记录二级阶段开始和截止时刻。
- `REJECT`：必须提供驳回原因，状态改为 `REJECTED`，保留审批历史，二级审批不得再操作。
- 审批人不可以修改申请的教室、时间、人数或用途；修改需求应撤销后重新提交，避免审核对象变化。

### M2-R10 二级审批与最终占用

仅当状态为 `PENDING_L2`，服务端当前时刻严格早于二级截止时刻，且操作者有终审权限并符合审批隔离规则时可以操作。

**驳回：**追加二级驳回记录，进入 `REJECTED`，未发生整室占用，不调用 D 执行“释放一间从未占用的教室”作为正常流程。

**通过：**在 M2 中以同一个审批请求标识锁定该申请的终审处理权，先将状态置为 `CONFIRMING`（正在向 D 确认），再经 D **原子**建立与该申请关联的整室占用。只有确认 D 成功、M2 保存对应占用引用之后，状态才进入 `APPROVED`。将二级审批通过的动作、处理人、时间和 D 确认结果关联记录，不能把“审批意见同意”直接等同于“可使用教室”。

终审时必须重新校验资源是否可用、教室开放时间和禁用状态是否仍合法，并要求 `now < startAt`。**R06 中“至少提前 2 小时”只在首次提交申请时检查，不能在终审时重新套用，否则正常的两级审批会被错误拒绝。**D 发现已有 M1 占用、其他 M2 占用或 M3 限制时，拒绝本次占用；M2 将申请结束为 `CONFLICT_FAILED`，清楚展示“审批阶段教室已不可用”，保留终审处理记录，不强行挤占任何已有预约。

若 D 网络调用超时/返回结果未知，不得立即认定失败并用新来源重复创建；应保留 `CONFIRMING`，以固定的 `applicationId` 和请求标识查询/幂等重试 D 的原操作，直至结果被确认或安全地清理。此期间页面显示“最终确认中”，不可宣称已批准。

### M2-R11 两级审批超时自动撤销（建议基线）

- 每个审批阶段最多等待 **24 小时**（从进入该阶段的时间起计算）。
- 每阶段实际截止时刻 = `min(该阶段进入时间 + 24 小时, 计划开始时间)`。
- 若处于 `PENDING_L1` 或 `PENDING_L2`，且服务端当前时间 `>=` 当前阶段截止时刻，则申请自动进入 `EXPIRED`，记录发生阶段和超时原因；这就是 M2 的“超时自动撤销”。
- 精确到边界：若截止时刻为 10:00:00，09:59:59 仍可审批，10:00:00 起不得再审批，无论定时任务是否运行。
- 已进入 `APPROVED` 的申请不因后续经过 24 小时而“审批超时”，而是在活动结束时完成。
- `CONFIRMING` 若跨过计划开始时间，必须先通过 D 的幂等查询/释放接口确认没有遗留占用，才能进入 `EXPIRED`；结果仍不确定时维持处理中并持续安全重试，不能假设从未占用。
- 超时任务正常运行时每 **60 秒**扫描一次；每次执行应幂等。**业务截止的判断以服务端时间为准，不能靠定时任务执行延迟延长可审批时间**。

### M2-R12 申请人主动撤销

- `PENDING_L1`、`PENDING_L2`：申请人可随时撤销，变更为 `WITHDRAWN`，当前/后续审批均不能再通过。由于待审从未占用资源，正常无需调用 D 释放。
- `APPROVED`：仅在 `now < startAt` 时申请人可撤销。必须调用 D 按该 `applicationId` 对应来源释放整室占用，并确认释放成功，才能对外返回撤销成功、进入 `WITHDRAWN`。
- `now >= startAt` 不支持申请人普通撤销；首迭代不实现活动进行中的主动提前结束。
- `CONFIRMING`：不直接进入终态，提示“正在确认占用，请稍后查看”，先消除占用结果的不确定性；保证不会留下失主的整室锁定。
- 终态申请不得再次撤销；重复提交同一次撤销，已成功时返回既有结果而不重复释放。

### M2-R13 正常结束

已批准申请在 `now >= endAt` 且未被撤销/系统取消时进入 `COMPLETED`，保留审批与占用历史。

D 的占用查询按预定时间边界判断是否有效：即使 M2 的完成定时任务延迟，`endAt` 之后不得继续阻止新的合法 M1/M2 预约。首迭代采用每 60 秒扫描完成状态，不需要申请人手动签退。

### M2-R14 拒绝、撤销与来源隔离

任何来源释放动作必须携带由 D 可核验的 `applicationId`/`occupancyId` 等唯一来源标识；只撤销本申请建立的整室占用，**不得直接将教室或所有座位设置为空闲**，也不得清除 M1 个人预约、其他 M2 预约、M3 限制或长期禁用标记。

M1 时间轴中的占用颜色由 D 基于所有有效来源计算；M2 不直接调用 M1 的数据库或修改座位状态。

## 五、状态机与操作记录

### 5.1 状态定义

| 状态 | 含义 | 是否应存在有效 M2 整室占用 |
| --- | --- | --- |
| `PENDING_L1` | 已提交，等待一级审批 | 否 |
| `PENDING_L2` | 一级已通过，等待二级审批 | 否 |
| `CONFIRMING` | 二级同意，D 最终占用确认未结束 | 不确定，必须向 D 核实 |
| `APPROVED` | D 已确认整室占用，已批准 | 在 `[startAt,endAt)` 有效 |
| `REJECTED` | 任一级人工驳回 | 否 |
| `EXPIRED` | 待审超时；或确认过程中超出开始时刻且资源已安全清理 | 否 |
| `WITHDRAWN` | 申请人合法主动撤销 | 否 |
| `CONFLICT_FAILED` | 二级通过后 D 明确拒绝建立整室占用 | 否 |
| `SYSTEM_CANCELLED` | 与紧急维修停用重叠而被系统撤销 | 否（需确保释放本来源的剩余占用） |
| `COMPLETED` | 活动到达计划结束时刻 | 历史保留，当前无有效占用 |

### 5.2 允许的状态流转

| 原状态 | 事件 / 条件 | 新状态 |
| --- | --- | --- |
| 无 | 新建申请资格与初步可用性通过 | `PENDING_L1` |
| `PENDING_L1` | 一级通过且未截止 | `PENDING_L2` |
| `PENDING_L1`、`PENDING_L2` | 当前级驳回 | `REJECTED` |
| `PENDING_L1`、`PENDING_L2` | 当前级到达截止时刻 | `EXPIRED` |
| `PENDING_L1`、`PENDING_L2` | 本人主动撤销 | `WITHDRAWN` |
| `PENDING_L2` | 二级通过并发起 D 原子占用 | `CONFIRMING` |
| `CONFIRMING` | D 确认占用成功且申请仍有效 | `APPROVED` |
| `CONFIRMING` | D 明确以资源冲突拒绝 | `CONFLICT_FAILED` |
| `CONFIRMING` | 已过开始时刻，确认无占用或已安全释放 | `EXPIRED` |
| `APPROVED` | 开始前本人撤销且释放成功 | `WITHDRAWN` |
| `APPROVED` | 到达结束时刻 | `COMPLETED` |
| `APPROVED` | 紧急停用命中且有效终止发生于预约结束前 | `SYSTEM_CANCELLED` |

**不允许**：跳过一级审批直接终审、终态重新激活、超时后补批、被驳回后修改原申请并恢复、批准后直接改教室或时段。可信的延迟停用事件若需要更正 `COMPLETED`，须保存独立更正记录，见 M2-R18。

### 5.3 审批记录与审计

每次成功审批、拒绝、撤销、超时、资源确认、紧急停用均记录：`applicationId`、原状态、新状态、操作者 ID（自动任务标记 `SYSTEM`）、操作时间、动作类型、可公开的原因、相关 `requestId`/D 来源 ID。

审批日志采取**追加记录**，不覆盖历史；至少记录 `stage`、`decision`、`reviewerId`、`decidedAt`、`comment`。同一申请同一审批阶段至多有一次有效的最终人工决策。所有失败的越权操作可按团队审计规范记录，但不能写入合法审批链。

## 六、M1 / D / M3 集成

### M2-R15 M2 → D → M1 整室占用

1. 申请处于任一待审阶段时，**不**在 D 创建实际整室占用，因此不应让 M1 时间轴提前变黄。
2. 二级人工同意后，M2 使用固定来源 `sourceModule=M2`、`sourceId=applicationId`，请求 D 建立该教室 `[startAt,endAt)` 的整室占用。
3. D 在**原子操作**中校验该教室内所有有效 M1 座位占用、其他 M2 整室占用、M3 整室停用和长期禁用；只在全部校验通过时建立来源占用。
4. 占用生效后，M1 查询 D 的对应教室全部座位时间轴，`[startAt,endAt)` 显示整室预约（黄色），并阻止个人预约。
5. M2 驳回/待审超时不会影响 M1（因为没有占用）；已批准预约在合法撤销或被系统取消后，只释放相应申请的占用，M1 刷新后恢复由其他来源决定的可用性。
6. 若 M1 正在与 M2 并发争用同一教室时段，D 最多允许冲突的一方成功，**不能两方均成功**。

### M2-R16 与 M1 既有预约冲突

**普通整室申请不具有强制清场权限。**只要目标时段任意座位存在已确认、仍有效的 M1 占用，D 就不得接受 M2 的整室占用。不得由 M2 擅自取消个人座位预约来“解决冲突”。

示例：某教室一个座位已有 `[10:00,11:00)` 的 M1 预约，则 M2 不得批准并实际占用 `[09:00,12:00)`；申请待审阶段本身不影响 M1 用户的使用权。

### M2-R17 M3 计划施工与普通维修

- 不影响教室正常使用的普通维修只显示提示，不阻止整室申请和批准。
- 未来计划施工若与已生效的 M2 整室占用冲突，按 M1 的跨模块规则由 D 拒绝建立该计划限制，M3 调整施工安排；不得用计划维修直接取消已经批准的 M2 预约。
- M2 不负责自行判断维修级别，也不得在用户申请或审批中设置“忽略维修限制”的开关。

### M2-R18 M3 紧急停用、系统取消与恢复

1. 对于立即停用的安全问题，M3 由授权人员确认停用范围、生效时间后，先向 D 建立停用限制，由 D 立即阻止新的占用，再通知 M2 处理受影响业务。
2. 若停用 `[stopFrom,stopTo)` 与已批准整室预约 `[startAt,endAt)` 相交，且停用生效时刻早于预约结束时刻，M2 将受影响的 `APPROVED` 预约置为 `SYSTEM_CANCELLED`，保留原计划区间、审批历史、停用工单/来源、生效时刻、处理时刻及系统取消原因。
3. 终止时刻为 `max(startAt, stopFrom)`（不得晚于 `endAt`）；M2 请求 D 释放本申请从终止时刻起剩余的有效占用，不影响此前已发生的使用历史。
4. 若通知到达时业务已记录为 `COMPLETED`，但可信停用生效时间位于原批准使用区间内，须保留更正日志，核实 D 资源事实并更正为 `SYSTEM_CANCELLED`；不得因通知晚到而抹除应有的停用影响。
5. M3 解除停用后，被系统取消的 M2 申请**不自动恢复**，申请人须重新走完整审批流程。若还有其他维修限制、M2 占用、M1 预约或长期禁用，D 继续保持对应限制。
6. 相同停用事件重复投递、解除和乱序投递时，用 `eventId` 与来源版本/生效时间幂等处理，不得重复取消、重复释放或误解除其他来源。若消息内容不足以判定，应向 D 查询来源当前状态，而不是凭消息顺序猜测。

> **集成契约待对齐**：M1 V0.4 约定 D 向 M1 转发停用结果。本稿建议同样由 D 向 M2 转发已确认的整室停用事件；如组内采用 M3 调用 M2 的公开接口，应通过 ADR 确认认证、重试和来源可信机制，业务行为不变。

### M2-R19 可追溯与错误处理

- 在 M2 申请中保存 `occupancyId`（如 D 返回）、`sourceId=applicationId`、调用请求号、最后一次确认结果；在 D 的限制/占用记录中能回溯 `M2` 来源与具体申请。
- 占用成功但 M2 保存失败时，不得返回“预约成功”；以同一来源查询 D 并完成业务记录恢复，或安全释放该来源占用。
- 释放请求超时/结果未知时，申请保持“撤销处理中/系统取消处理中”的内部操作状态或任务记录，不提前返回已经释放的结论。使用同一来源幂等重试。
- 若 D 暂时不可用，页面/接口返回清晰错误，不能退化为 M2 单独写表并宣称资源已占用。
- 首迭代只需可重试的后台检查/补偿任务和日志，不强制建设独立分布式事务协调平台；跨模块失败不能被静默忽略。

## 七、后端接口契约（建议草案）

> **注意：以下路径和 DTO 是为 AI 对接提供的建议，不意味着 D 已经实现同名接口。**先检查现有项目路由、用户鉴权、D 的 OpenAPI/接口文档与数据结构；与已存在约定冲突时优先复用，并更新本节及接口测试。所有接口均需要服务端权限校验。

### 7.1 M2 对外 HTTP API

| 方法 | 建议路径 | 请求/筛选要点 | 权限 | 功能 |
| --- | --- | --- | --- | --- |
| `GET` | `/api/m2/classrooms` | `building`、分页 | `M2_APPLY` | 有权申请的教室列表（从 D 读取/代理） |
| `GET` | `/api/m2/classrooms/{roomId}/availability` | `startAt`、`endAt` | `M2_APPLY` | 查询 D 的教室可用性快照 |
| `POST` | `/api/m2/applications` | 申请表单、`Idempotency-Key` | `M2_APPLY` | 创建待审申请 |
| `GET` | `/api/m2/applications/my` | `status`、`page`、`size` | 已登录 | 本人申请列表 |
| `GET` | `/api/m2/applications/{id}` | 路径 ID | 归属或审批范围 | 申请详情与审批历史 |
| `POST` | `/api/m2/applications/{id}/withdraw` | `Idempotency-Key` | 申请本人 | 合法撤销 |
| `GET` | `/api/m2/approvals/tasks` | `stage`、`status`、分页 | 对应审批角色 | 本级审批待办/历史 |
| `POST` | `/api/m2/applications/{id}/decisions` | `stage`、`decision`、`comment`、幂等键 | 当前级审批人 | 本级通过/驳回 |

**创建请求 JSON 示例（字段名按现有项目习惯调整）：**

```json
{
  "roomId": "ROOM-101",
  "startAt": "2026-11-02T09:00:00+08:00",
  "endAt": "2026-11-02T11:00:00+08:00",
  "purpose": "学院学生学术交流活动",
  "participantCount": 35
}
```

**审批请求 JSON 示例：**

```json
{
  "stage": 2,
  "decision": "APPROVE",
  "comment": "符合活动场地使用规定"
}
```

示例只说明格式，并非可在任意服务器时刻提交的有效测试数据；自动化测试应使用可控制的时钟生成时间，避免固定日期过期。

建议错误结构统一：`{ "code": "...", "message": "...", "details": { ... } }`。稳定错误码至少有 `UNAUTHORIZED`、`FORBIDDEN`、`INVALID_TIME`、`INVALID_APPLICATION`、`ROOM_UNAVAILABLE`、`APPROVAL_STAGE_MISMATCH`、`APPROVAL_EXPIRED`、`SELF_APPROVAL_FORBIDDEN`、`RESOURCE_CONFLICT`、`ALREADY_FINALIZED`、`DEPENDENCY_UNAVAILABLE`、`RESULT_PENDING`。

建议 HTTP 语义：认证缺失 `401`、权限不足 `403`、参数错误 `400`、对象不存在或无权查看时统一不泄露细节 `404`、状态竞争/资源冲突 `409`、外部依赖失败 `502/503`。重试是否安全由幂等标识决定。

### 7.2 M2 与 D 最小能力契约

M2 需要 D 实际提供以下**能力**，但不应在 M2 内编写模拟的“生产替身”冒充已联调：

| 能力 | 建议请求要素 | 必要返回/保证 |
| --- | --- | --- |
| 获取本人权限与资源范围 | 来自可信认证上下文的用户标识 | 角色、可申请/可审批资源范围 |
| 查询教室主数据 | `roomId`、当前用户权限范围 | 容量、开放时间、可用状态、是否支持整室预约 |
| 查询整室可用性 | `roomId`、`[startAt,endAt)` | 所有会阻断整室使用的来源，查询失败明确报错 |
| 原子建立整室占用 | `sourceModule=M2`、`sourceId=applicationId`、`roomId`、时间段、幂等键 | 原子冲突检查；成功返回占用引用；同源重复调用不重复建立 |
| 查询来源占用结果 | `sourceModule`、`sourceId` 或固定请求号 | 能区分不存在、已生效、已释放及未知结果 |
| 按来源释放剩余占用 | `sourceModule`、`sourceId`、必要时 `releaseFrom` | 不触及其他来源；调用幂等，可核实结果 |
| 获取/接收整室紧急停用 | 可信 `eventId`、工单/来源、范围、时间、版本 | 先由 D 生效限制，再通知业务模块；可重试并可查询 |

**必须与 D 组共同确认的原子性条款**：M2 占用与任何 M1 座位占用（包括并发创建）不能互相绕过；创建与取消均按来源隔离。D 如果尚无相关能力，M2 应先实现接口适配层和契约测试，待 D 提供正式实现后联调，不得直接访问 D 的数据库绕过该能力。

### 7.3 内部回调接口（示意）

可采用 `POST /internal/m2/resource-restrictions` 接收 D 的已确认停用事件，或采用现有公开的内部事件接口。必须具备服务间鉴权、`eventId` 去重、来源版本判定、幂等重放及失败重试机制。禁止匿名客户端伪造紧急维修事件以取消他人教室申请。

## 八、数据模型与持久化建议

> 表名/列名仅为逻辑模型草案。实际开发应复用项目已有数据库、ORM、命名风格，并提交版本化迁移脚本与幂等种子数据；不可手工修改测试/生产数据库。

### 8.1 `m2_applications`（申请主表）

| 字段 | 说明 |
| --- | --- |
| `id` | 申请唯一 ID |
| `applicant_id` | 来自 D 可信身份的申请人 ID |
| `room_id` | 引用 D 的教室 ID，不在 M2 重建教室主数据 |
| `start_at`, `end_at` | 计划时段，统一时区规范 |
| `purpose`, `participant_count` | 用途、预计人数 |
| `status`, `version` | 业务状态、乐观锁版本号（或等效行级锁） |
| `created_at`, `updated_at` | 创建/更新时间 |
| `l1_entered_at`, `l1_deadline_at` | 一级阶段开始及截止 |
| `l2_entered_at`, `l2_deadline_at` | 二级阶段开始及截止 |
| `occupancy_id`, `occupancy_request_id` | D 占用引用与固定调用标识，可为空 |
| `cancel_reason`, `cancelled_at` | 撤销/系统取消/超时原因与时间 |
| `maintenance_source_id`, `maintenance_effective_at` | 紧急维修来源和可信生效时刻，按需为空 |
| `completed_at` | 完成时间，按需为空 |

### 8.2 `m2_approval_records`（不可覆写的审批记录）

字段建议包括：`id`、`application_id`、`stage`（1/2）、`reviewer_id`、`decision`（`APPROVE`/`REJECT`）、`comment`、`decided_at`、`request_id`。通过事务及唯一约束保障每级只有一个有效最终审核结果。

### 8.3 `m2_operation_records`（关键操作及恢复记录）

记录业务操作 ID、申请 ID、类型、幂等键、外部请求号、执行结果（`PENDING`/`SUCCESS`/`FAILED`）、重试次数、最近错误、发生时间、完成时间。用于 D 结果未知时的恢复与审计，不要求建设复杂通用消息系统。

### 8.4 并发约束与迁移

- 同一个申请的状态变更必须通过行级锁、版本号 CAS 或等效事务机制串行化，不能两个审批请求同时成功推进不同状态。
- `applicationId` 唯一，申请人和 `Idempotency-Key` 组合唯一（或语义等价的去重表）；已确认审批阶段的有效决定有唯一约束。
- 索引至少支持 `applicant_id + created_at`、`status + deadline`、审批人待办所需状态/范围检索。
- Schema 迁移从空库可完整重放；种子数据仅用于测试/演示并幂等执行。不能把示例申请人/审批人密码、固定 token 或明文密钥提交到版本库。

## 九、异常、一致性与工程质量

### M2-R20 原子状态流转

每个影响状态的操作均由后端核对身份、当前状态、审批阶段和服务端时刻，并使用事务/版本检查。并发“审批 vs 超时”“批准 vs 撤销”“多人同时审批”至多形成一个合法最终结果。

对 `CONFIRMING`、撤销中、紧急取消中等跨服务操作，保留持久化的待处理请求号；服务重启后可继续核对，不得仅将未完成状态放在进程内存中。

### M2-R21 后台作业

使用正常运行时约每 60 秒执行的可重复任务：

1. 扫描一级/二级审批逾期的待审申请，按 R11 幂等设为 `EXPIRED`。
2. 扫描应完成的已批准申请，按 R13 更新 `COMPLETED`。
3. 扫描 `CONFIRMING` 或跨模块释放结果未知的操作，按固定来源向 D 查询并完成确认、重试或清理。
4. 如有未完成的可信紧急停用通知，继续核实来源及幂等处理。

定时任务不得用“扫描运行时间”替代真实业务截止条件。可重复执行、重启后继续、超时不多次生成审批或占用记录。

### M2-R22 错误与隐私

对未登录、角色不符、审批越权、时间非法、人数超额、不可用、审批超时、状态竞争、D 不可达和 D 返回未知结果，提供可理解的错误码/提示。对无权查看的申请不要泄露存在性或审批详情。

日志中不得记录凭证、完整认证 token、敏感联系信息。保留必要的用途、审批意见与审计记录，但不得把这些信息加入任何普通用户可见的公共时间轴。

### M2-R23 工程交付要求

- 将规格、项目级规则文件（如 `AGENTS.md`）、架构/接口决策、接口文档、测试、迁移脚本与 CI 配置纳入 Git。
- 构建与测试失败不得合并；跨模块契约、公共层或 schema 变化需要组内评审。
- 测试应验证真实业务行为，不允许只断言常量或 mock 掉被测逻辑；至少对一项关键测试用“故意破坏实现”证明其确实失败。
- 本模块部署遵循项目组统一测试/生产环境与版本 tag；生产发布按小组规定进行人工审批并能回滚。
- 不在 M2 内自建另一套登录、教室资源数据库或 CI/容器编排体系，尽量复用已有平台结构。

## 十、首迭代范围与后续事项

### 10.1 第一迭代必须完成（P0）

1. 登录授权与 M2 角色门槛；有权申请的教室/时段查询。
2. 表单申请提交及本人的申请列表/详情/撤销。
3. 两级人工审批的待办、通过、驳回、角色与顺序控制。
4. 24 小时/开始时刻双重截止下的审批超时自动撤销。
5. 终审通过后经 D 原子建立整室占用；占用失败明确展示，M1 座位时间轴联动。
6. 已批准且尚未开始时的申请撤销与来源占用释放；到期自然完成。
7. M3 紧急停用的接收与安全取消闭环（在 D/M3 联调具备后验收）。
8. 状态审计、基本异常/幂等恢复、数据库迁移、真实单元/接口/集成测试。

### 10.2 暂缓到后续迭代（P1）

站内通知中心、邮件/短信通知、临近活动提醒、电子签章、审批转交/加签、复杂流程配置器、申请材料上传、日历导出、活动进行中的主动提前结束、细粒度运营报表、长期场地周期性预约、自动调度候选教室、自动强制清退既有 M1 预约。

**P1 不得破坏 P0 正确性**；尤其不能为实现“自动换教室”绕过 D 的原子占用机制。

### 10.3 待项目组确认的参数与契约

| 决策点 | 本稿采用的建议默认值 | 修改时要求 |
| --- | --- | --- |
| 申请资格 | D 中显式授予 `M2_APPLY` | 由 D 组确认权限配置与人员范围 |
| 审批责任 | 2 级人工，一级院系/区域，二级校级/终审 | 明确审批人及教室管理范围，禁止本人审批 |
| 申请开放范围 | 最迟开始前 2 小时、最早提前 14 天 | 若调整，更新规则、表单与边界测试 |
| 申请时长 | 1～8 小时，半小时粒度 | 与教室开放时间和 D 资源能力校验一致 |
| 审批时限 | 每级 24 小时，且不晚于计划开始 | 统一服务端截止判断和定时任务 |
| D 资源接口 | D 原子建立/查询/释放 `M2` 来源整室占用 | 开发前确认接口、鉴权、幂等和错误码 |
| M3 通知链路 | D 先建限制再通知 M2 | 明确回调认证、事件 ID、延迟及重试 |
| 撤销中/占用确认中 | 对外显示处理中，后台持久化核实结果 | 不得假成功或遗留来源占用 |

## 十一、核心验收场景（测试应可自动执行）

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| M2-T01 | 未登录提交/审批 | `401`，无业务变化 |
| M2-T02 | 只有 M1 座位权限的学生创建 M2 申请 | `403`，不因 M1 权限自动获批 |
| M2-T03 | 用户提交自己无权限访问的教室 | 拒绝，不暴露无权限信息 |
| M2-T04 | 时间不在开放区间、跨日、非半小时边界或长短不合规 | 后端拒绝；不产生申请 |
| M2-T05 | 开始时间恰好为当前时间+2小时、略早于此时间 | 前者满足最低提前量，后者拒绝（其他条件相同） |
| M2-T06 | 申请时段已有一个有效 M1 座位预约 | 申请可用性预检拒绝；不得强制取消 M1 |
| M2-T07 | D 无法查询可用性 | 创建失败并给出依赖错误；不假设空闲 |
| M2-T08 | 相同申请人的同一 `Idempotency-Key` 重试 | 返回同一申请 ID，不重复建单 |
| M2-T09 | 提交申请成功 | 状态为 `PENDING_L1`；D 无整室占用；M1 不提前变黄 |
| M2-T10 | 一级审批人通过 | 变成 `PENDING_L2`；仅记录一级审批；D 仍无整室占用 |
| M2-T11 | 一级直接驳回/二级直接驳回 | 分别成为 `REJECTED`；原因可见；没有 D 整室占用 |
| M2-T12 | 二级在一级通过前尝试审批 | 拒绝，状态和日志不被越级篡改 |
| M2-T13 | 申请人自己审批，或同一人同时审两级 | 拒绝；不得因兼有角色放行 |
| M2-T14 | 非管理范围内的审批人审单 | `403`；申请不变 |
| M2-T15 | 两人并发审批同一待办 | 至多一个审批操作推动状态；审批日志不重复 |
| M2-T16 | 截止时间前 1 秒与恰好截止时刻审批 | 前者满足时间条件；后者拒绝且进入/最终收敛到 `EXPIRED` |
| M2-T17 | 一级已等待 24 小时；二级尚未截止 | 仅超时对应阶段；另一条申请不受影响 |
| M2-T18 | 定时任务延迟执行后才发起过期审批 | 不因任务延迟放行；最终记超时 |
| M2-T19 | 二级通过，D 成功建立整室占用 | 状态 `APPROVED`，占用来源 M2 可追溯，所属全部座位对应时段黄色且无法再约 |
| M2-T20 | 已有 M1 预约与 M2 终审确认并发发生 | D 最多一方成功；失败方保持正确业务状态；M1 不被强制取消 |
| M2-T21 | 两个不同 M2 申请竞争同一教室重叠时段 | 最多一个建立整室占用；另一个 `CONFLICT_FAILED` |
| M2-T22 | 终审调 D 超时且 D 可能已创建占用 | 保持 `CONFIRMING` 并幂等核实，不重复占用、不假成功 |
| M2-T23 | 待审申请本人撤销，随后原审批人点击通过 | 申请停留 `WITHDRAWN`，不建立占用 |
| M2-T24 | 已批准申请在开始前本人撤销 | 仅释放本申请来源，占用消失，其他来源保持 |
| M2-T25 | 已批准申请在开始时刻/开始后尝试本人普通撤销 | 拒绝；不直接释放进行中的占用 |
| M2-T26 | 正常活动结束，完成定时任务尚未运行 | D 时段自然失效，不阻止后续相邻时段合法预约；最终转 `COMPLETED` |
| M2-T27 | 普通维修提示或未来计划施工与现有 M2 占用冲突 | 普通维修不影响；冲突计划停用按 D 规则被拒，不自动取消已批准申请 |
| M2-T28 | M3 紧急停用与已批准 M2 预约重叠 | D 首先阻断新占用；M2 `SYSTEM_CANCELLED`，保留来源/时刻，释放剩余占用 |
| M2-T29 | 停用事件重复/乱序/延迟至自然完成之后 | 依据可信生效时间处理/更正，幂等，无误解除其他来源 |
| M2-T30 | M3 解除一张工单，但仍有其他有效限制 | 不自动恢复为可预约；已系统取消的 M2 申请不复活 |
| M2-T31 | 申请人查看他人的申请或普通用户查看审批隐私 | 拒绝或仅返回脱敏的占用原因 |
| M2-T32 | 空库运行迁移+种子脚本两次 | 结构可建立，脚本幂等，无重复种子数据 |
| M2-T33 | 故意破坏冲突判断或审批截止判断后运行测试 | 对应自动化测试必须失败，证明测试真正验证行为 |

**通过标准**：每项 P0 功能有对应的代码位置、接口/页面演示步骤和自动化测试编号；无法在首迭代实现的 P0 条目仍保留于追踪表并明确状态、原因与依赖，不从需求中删除。

## 十二、给 AI 的实施指令

> 本节可以连同整份 Markdown 一起交给 AI。AI 应先给出实施方案、拟修改文件与风险说明，再按阶段编码；不要一次性大改仓库。

### 12.1 首先检查仓库，不要假定技术栈

1. 阅读仓库已有 `AGENTS.md`、README、M1 与 D 的接口规范、迁移脚本、测试命令、前后端目录结构。
2. 列出可复用的认证、RBAC、HTTP 客户端、错误结构、时间工具、数据库/事务/定时任务与 CI 方案。
3. 对照本文件第十节列出尚未确认的 D 接口与项目组决策点；区分“可以立刻开发 M2”与“必须等待 D/M3 接口”的功能。
4. 先输出：模块目录计划、表设计、状态图（文字即可）、接口计划、关键并发/失败方案、测试计划及分批实现顺序。**得到人工确认或遵照现有项目约定后再修改生产代码。**

### 12.2 建议编码顺序

- **阶段 A：基础能力**。数据库迁移、M2 角色授权适配、申请模型和只读查询、申请创建、本人记录/详情、幂等提交。编写单元/接口测试。
- **阶段 B：审批闭环**。一级/二级审批、状态并发约束、驳回、审批截止和定时任务，补边界与权限测试。
- **阶段 C：D 占用闭环**。终审 `CONFIRMING`、D 原子确认、冲突失败、已批准撤销、按来源释放、自然完成、失败重试和 M1 联调测试。
- **阶段 D：维修联动**。接收 D/M3 停用事件、系统取消、延迟/重复处理、多来源恢复测试，完成审计与跨模块演示。
- **阶段 E：前端与交付**。申请页、我的申请、审批工作台、错误反馈、运行/测试说明与 CI，确保与后端真实交互。

### 12.3 AI 实现约束

- 不改写 M1 的个人座位预约规则，不实现另一套 D 占用引擎，不直连其他模块业务表。
- 不得因接口未就绪而在生产模式用“永远空闲”“永远占用成功”的假实现。**测试**可以使用受控 fake/mock D，但必须另有契约测试及可替换的生产 D 适配器。
- 所有业务校验在后端完成；所有状态操作具备权限、时间、当前状态和幂等判断。
- 数据模型改动必须附带版本化数据库迁移；所有关键外部调用要有来源 ID 和可诊断日志。
- 对每个需求 ID `M2-Rxx`/`M2-Fxx` 提供实现位置及对应测试，重点覆盖 T01～T33。
- 每个阶段尽量形成可审查的小提交；不自行解决不明确的跨模块协议冲突或自动合并冲突，应写明分歧请组内评审。
- 测试与运行说明使用仓库实际命令，不凭空编写“已通过”或“已部署”的结论。

### 12.4 交付检查清单

- [ ] 申请人能查询教室、提交申请、查看本人记录、撤销合法申请。
- [ ] 一级与二级审批顺序、权限、驳回、超时和自我审批限制可验证。
- [ ] 二级批准且 D 占用成功后，M1 相应时段全部座位阻止新预约，来源可追溯。
- [ ] 并发终审/M1 预约不能同时占用冲突资源。
- [ ] 合法撤销、超时、冲突失败、紧急停用及正常结束不会留下无主占用。
- [ ] 主要失败路径能恢复/重试，状态与界面不误报成功。
- [ ] 迁移、种子、测试、运行文档与需求映射完整提交。
