# M3 物业报修工单模块需求规格说明书 V0.2

> 项目名称：校园资源服务平台  
> 模块：M3 — 物业报修工单  
> 版本：V0.2  
> 状态：**需求评审稿 / 开发输入稿（尚未实现或验收）**  
> 适用阶段：第一次功能迭代，兼顾后续跨模块联调  
> 关联模块：D（公共资源、身份权限、统一占用）、M1（个人自习座位预约）、M2（整教室预约与审批）  


## 一、模块目标与边界

### 1.1 业务目标

M3 面向校园用户提供教室故障报修与进度查询，面向物业人员提供评估、派单、维修、超时处理和验收功能。工单完成后由报修人评价一次，所有结果保留历史。

主流程：

`提交报修 → 评估故障及使用影响 → 人工派单 → 维修人员开始处理 → 提交完工 → 独立验收 → 完成 → 报修人评价`

需要停用的工单，另行执行：

`授权人员确认范围与时刻 → D 建立限制 → D 协调 M1/M2 → 维修与验收 → 确认安全恢复 → D 解除本来源限制`

**工单进度和资源限制分别记录**："已派单"不代表限制已生效，"提交完工"不代表可以重新预约，"工单完成"也不保证教室没有其他来源的限制。

### 1.2 职责划分

**M3 负责：**

- 报修记录、紧急度与使用影响评估、派单、维修进度、超时升级、验收、评价。
- 向 D 申请建立/变更/解除维修限制，并保存来源追溯信息。

**D 负责（不在 M3 内重复实现）：**

- 统一认证、RBAC、用户可报修/可管理的教室范围、维修人员资格。
- 教室与座位主数据（存在、归属、禁用状态）。
- 按来源原子建立/查询/解除限制，统一判断与 M1/M2 占用的冲突，并协调受影响模块。

**M1 / M2 负责：**

- M1 负责个人预约的系统取消、违约更正、额度重算与历史保留；M2 负责整室预约的系统取消、来源占用释放与审批历史保留。M3 不直接修改任何预约数据。

**权威边界**：M3 是"工单、维修判断与验收事实"的权威；D 是"物理资源是否可被占用"的权威。模块间只通过已授权的公开 HTTP 接口交互，**严禁 M3 直接读写 D、M1、M2 的内部业务表**。

### 1.3 首迭代原则

1. **安全优先**：确认安全问题立即整室停用，先阻断新预约、再处理存量预约；普通维修不阻断任何预约。
2. **人工分级**：评估、派单、验收、停用确认、安全恢复分属不同授权；验收人不得验收自己参与的维修。
3. **权限后端校验**：按钮是否显示不能代替接口授权。
4. **资源以 D 为准**：M3 只提交限制申请，冲突由 D 原子判定；前端预检结果只是快照。
5. **可追溯、可恢复**：停用、恢复、系统取消按来源记录；D 结果未确认时不误报成功。
6. **控制范围**：阻断只到整间教室；超时用普通定时任务处理，不引入消息队列或独立补偿平台。

## 二、用户角色与权限控制

### M3-R01 登录与可信身份

所有查询和操作均须登录。报修人、维修人、验收人从 D 的可信认证上下文获取，不接受请求体中的 `reporterId`、`operatorId` 作为实际操作者。

未登录返回 `401`；无操作权限返回 `403`；对无权读取的工单统一返回不泄露存在性的 `404`。每次操作重新检查权限、资源范围、工单归属和状态。

### M3-R02 角色与管理范围

建议由 D 配置以下权限（名称可随现有 RBAC 契约映射）；一个岗位可持有多种权限，但不能绕过 R03 的验收隔离：

| 权限标识（建议） | 允许操作 | 范围限制 |
| --- | --- | --- |
| `M3_REPORT` | 提交报修、查询本人记录、合法取消、完成后评价 | 有权报修的教室及本人记录 |
| `M3_DISPATCH` | 评估、驳回、派单、改派、查看升级记录 | 被授权管理的教室 |
| `M3_WORK` | 开始维修、提交进度、提交完工 | 当前分配给本人的工单 |
| `M3_ACCEPT` | 验收通过或退回 | 被授权验收的教室 |
| `M3_RESOURCE_CONTROL` | 确认停用/影响变更、确认安全恢复 | 被授权管理的教室 |

普通学生不因具有 M1 预约权限就能派单、停用或恢复教室。本人历史查询只要求登录和归属校验，不因失去新建报修资格而丢失。

### M3-R03 验收隔离与隐私

- 验收人不得是本轮维修的实际处理人员；改派前后参与本轮维修的人都计入处理人员，不能靠改派规避自验收。
- 报修人评价不能替代技术验收，也不能直接解除停用。
- 报修人只看本人工单；维修人员只看分配任务及履职必需的历史；调度和验收人员只看其管理范围。
- 公共维修提示只包含教室、影响时段、公开原因和处理提示，不返回报修人身份、维修人员私人信息、完整故障描述、评价或内部意见。

## 三、页面与查询需求

### M3-F01 故障上报

用户选择 D 返回的可报修教室（长期禁用的教室仍可报修，不能只列出可预约教室），可附选该教室内的座位用于定位，再填写故障类别、标题、描述，可勾选"疑似影响安全"。

提交成功显示工单编号（编号规则实现时确定）和"已提交，待评估"。勾选疑似安全不会自动停用教室，页面须说明仍待授权人员评估，并将此类工单优先展示给调度人员。

### M3-F02 我的报修

分页查询本人记录，支持按日期、教室和状态筛选。详情展示报修信息、当前阶段、公开处理进展、是否停用、预计处理时间、实际完工/验收时间、驳回或取消原因及可执行操作。

限制申请或解除结果未知时显示"停用同步中""恢复同步中"，不显示为已停用或已恢复。查询失败提供错误与重试入口，不用空列表冒充无工单。

### M3-F03 调度工作台

按管理范围展示待评估、待派单、处理中和超时工单，可按教室、状态、影响类型、疑似安全标记筛选。支持评估、驳回、派单和改派；同时展示限制同步失败和超时升级，避免只按工单状态筛选而漏掉安全操作。

### M3-F04 维修工作台

维修人员查看本人任务、教室定位、故障信息、计划窗口和历史，执行开始维修、追加进度、提交完工。提交完工须填写处理结果；不能自行设置"验收通过"或"教室恢复"。

### M3-F05 验收与评价

验收人员查看本范围待验收记录、维修结果及必要历史，提交通过或退回。涉及停用的工单同时展示安全恢复确认和 D 解除结果。报修人在工单完成后提交评分及可选文字评价。

### M3-F06 预约页面维修提示

M1/M2 通过统一资源信息显示普通维修提示和有效停用区间。普通维修不覆盖个人蓝色或整室黄色；停用显示红色并附文字原因。多来源原因全部保留，主色优先级遵循 M1 的"红色 > 黄色 > 蓝色"，不以颜色代替后端冲突判断。

## 四、报修与工单处理规则

### M3-R04 报修内容校验

首迭代建议字段：

| 字段 | 规则 |
| --- | --- |
| `roomId` | 必填，教室存在且当前用户可报修，从 D 核验 |
| `seatId` | 可选，若填写必须属于该教室；只用于定位，不产生座位级阻断 |
| `category` | `ELECTRICAL` 电气 / `LIGHTING` 照明 / `FURNITURE` 家具 / `ENVIRONMENT` 环境 / `OTHER` 其他 |
| `title` | 去首尾空白后 5～80 个字符 |
| `description` | 去首尾空白后 10～1000 个字符 |
| `suspectedSafetyIssue` | 布尔值，用户提供的评估线索，不是停用授权 |

不要求上传图片、手机号或定位。D 不可达时明确返回依赖错误，不伪造教室存在或授权结果。不同用户可对同一教室重复报修，不自动合并或删除；调度人员可关联已有工单，但各自记录和来源仍保留。

### M3-R05 幂等提交与操作

创建及各写操作携带唯一 `Idempotency-Key`。服务端按"认证用户 + 操作类型 + 目标工单 + 幂等键"绑定请求内容；创建以用户和操作类型为范围。

同键同内容返回已有结果或处理中进度；同键不同内容返回 `409`，不覆盖原请求。同一次派单、完工、验收和评价重试不产生重复有效记录。幂等查询仍须检查当前访问权限。

### M3-R06 故障评估

调度人员核对故障是否有效、紧急度和处理安排；`M3_RESOURCE_CONTROL` 持有人确认资源影响，记录理由、范围、操作者和判断时间。只有调度权限不能确认安全停用或恢复。

处理紧急度与资源影响是两个独立维度：

| 紧急度 | 含义 |
| --- | --- |
| `NORMAL` | 常规处理 |
| `URGENT` | 优先处理，用于疑似或确认的安全问题 |

| 资源影响 | 含义 | 预约处理 |
| --- | --- | --- |
| `UNASSESSED` | 尚未确认是否影响使用 | 可展示待评估提示 |
| `NOTICE_ONLY` | 确认不影响正常使用 | 仅提示，不创建阻断限制 |
| `PLANNED_STOP` | 当前安全，未来施工需整室停用 | 按获准区间预先建立限制，冲突则调整安排 |
| `EMERGENCY_STOP` | 确认必须立即整室停用 | 立即请求 D 阻断，再协调已有预约 |

- 标记 `URGENT` 不自动获得取消预约的权限；未评估的工单不得开工。
- 紧急停用不必等待评估表单其余字段、派单或维修开始。
- 新报修默认 `NORMAL`，勾选疑似安全问题时按 `URGENT` 优先排队；授权人员可按事实调整并留痕。
- 确认 `EMERGENCY_STOP` 的工单至少按 `URGENT` 计时。

### M3-R07 派单与改派

通过有效性评估、影响已确认且未处于终态的工单，调度人员可指定一名当前负责的维修人员，记录派单原因和时间。第一版采用人工派单，不要求自动匹配、抢单或接单审批。

- `SUBMITTED → ASSIGNED`；已有 `ASSIGNED` 工单可改派，状态不变。
- `IN_PROGRESS` 工单改派须记录交接说明，状态仍为维修中；旧处理人立即失去后续写入权限，已提交的记录保留。
- 两个调度人员并发派单只能形成一个有效当前分配。
- 紧急限制尚在同步时可以安排人员，但不能因此宣称资源已被阻断。
- 首次派单时间与本阶段截止不因改派重置。

### M3-R08 开始维修与进度

仅当前维修人员可把 `ASSIGNED` 改为 `IN_PROGRESS`，记录实际开始时间。开始维修**不自动创建停用**：普通维修保持提示；需停用的施工须先核实 D 已确认相应限制生效，计划施工还须到达获准开始时刻。

维修人员可追加进度，建议每条 1～1000 字符，不能修改他人已提交内容。发现新安全隐患时应立即请求授权资源管理人员确认升级，不得继续以普通维修标记掩盖已确认的停用需求。

### M3-R09 提交完工

仅当前维修人员可在 `IN_PROGRESS` 提交处理结果，建议 5～1000 字符。记录本轮完工时间，状态进入 `PENDING_ACCEPTANCE`，保留实际维修过程。

提交完工不自动验收、不直接解除停用。重复提交同一操作返回既有结果；改派和完工并发时，以串行状态校验确定唯一合法结果。

### M3-R10 验收通过与退回

授权且符合 R03 隔离规则的验收人员处理 `PENDING_ACCEPTANCE`：

- **退回**：必填 5～500 字符原因，回到 `IN_PROGRESS`，保留原完工和验收记录，开启新一轮返修及截止，不删除旧超时记录。原负责人资格失效时由调度改派。
- **通过**：记录技术验收结论。无未解除限制、无待发送或在途资源操作的普通工单，在撤除本工单提示后进入 `COMPLETED`；有停用的工单还须满足 R20 的安全恢复与按来源解除条件，解除未确认时停留在待验收阶段并显示"验收通过，恢复同步中"。解除结果确认后由恢复任务核对全部完成条件并进入 `COMPLETED`，不要求重复提交同一轮验收。

每一维修轮次至多一条有效验收决定。验收通过并开始恢复后，普通退回请求不能覆盖在途恢复操作；发现新的不安全事实须按 R20 重新建立有效限制并留痕。

### M3-R11 报修人取消与管理驳回

报修人仅可在 `SUBMITTED`、尚未派单、无已确认停用要求且无生效限制、无待发送或在途资源操作时取消，填写原因后进入 `CANCELLED`。已派单、维修中或待验收不能由报修人取消，可通过工单反馈说明情况。

调度人员仅可对尚未派单且无已确认停用要求、无生效限制、无待发送或在途资源操作的无效报修执行 `REJECTED`，须填写原因；因重复报修驳回时可关联真实有效的原工单，但不删除记录。

已有停用要求的工单不通过"取消/驳回"解除限制；取消与首次派单并发时只能一个成功。终态不接受普通重新激活，新故障重新建单并关联历史。派单前发现停用判断有误的，按 R20 的更正流程安全清理后，可重新按本节条件取消或驳回，原判断与清理历史保留。

### M3-R12 完成后评价

仅报修人可对本人 `COMPLETED` 工单评价一次，建议整数评分 1～5、可选文字不超过 500 字符。已取消、驳回或尚未完成不能评价；不同幂等键重复评价返回 `409`，同键重试返回既有结果。

评价不改变工单、验收或资源状态。第一版不设匿名公开排行榜、不把低分自动转成处罚或重新停用；评价只向报修人和被授权的本范围管理人员展示。

## 五、状态机与时间规则

### 5.1 工单状态

| 状态 | 含义 | 可执行的主要操作 |
| --- | --- | --- |
| `SUBMITTED` | 待评估或待派单 | 评估、派单、条件满足时取消/驳回、紧急停用 |
| `ASSIGNED` | 已指派，尚未开始 | 改派、开始、影响变更 |
| `IN_PROGRESS` | 维修或返修中 | 追加进度、改派、提交完工、影响变更 |
| `PENDING_ACCEPTANCE` | 待验收，或已通过但资源恢复处理中 | 通过、退回、查询/恢复限制操作 |
| `COMPLETED` | 验收通过且本工单限制已确认解除或不存在 | 评价、历史查询 |
| `REJECTED` | 无效报修被管理人员驳回 | 历史查询 |
| `CANCELLED` | 报修人在允许条件下取消 | 历史查询 |

### 5.2 允许的状态流转

| 原状态 | 事件 / 条件 | 新状态 |
| --- | --- | --- |
| 无 | 报修创建并通过校验 | `SUBMITTED` |
| `SUBMITTED` | 评估完成并由调度派单 | `ASSIGNED` |
| `SUBMITTED` | 报修人按 R11 取消 | `CANCELLED` |
| `SUBMITTED` | 调度按 R11 驳回 | `REJECTED` |
| `ASSIGNED` | 当前维修人开始维修 | `IN_PROGRESS` |
| `IN_PROGRESS` | 当前维修人提交完工 | `PENDING_ACCEPTANCE` |
| `PENDING_ACCEPTANCE` | 验收退回（开启新一轮返修） | `IN_PROGRESS` |
| `PENDING_ACCEPTANCE` | 验收通过，普通工单且提示已撤除，无未解除限制及待处理资源操作 | `COMPLETED` |
| `PENDING_ACCEPTANCE` | 验收通过，但停用尚未确认解除 | 保持 `PENDING_ACCEPTANCE`（显示"验收通过，恢复同步中"） |
| `PENDING_ACCEPTANCE` | 已验收通过，安全恢复已确认，全部本来源限制已解除或确认不存在，无待处理资源操作且提示已撤除 | `COMPLETED` |
| `PENDING_ACCEPTANCE` | 恢复中发现新隐患，按 R20 确认新限制并开启返修轮次 | `IN_PROGRESS` |

**不允许**：跳过评估/派单直接开工、未完工先验收、终态重新激活、驳回后修改原工单复活。通常影响变更、紧急停用与超时升级只作用于资源限制和升级记录，不改变工单状态；R20 定义的恢复中新隐患返修为例外，必须保留原验收结论及其不再满足当前恢复条件的原因，并开启新轮次。

### 5.3 资源同步状态

工单与限制是一对多关系，每次限制操作有独立来源与版本。资源同步状态表达该来源的确认进度；操作记录另行区分待发送、调用中、结果未知和已结束，不能把本地持久化等同于请求已经发往 D。本文"在途"指已向 D 发出请求但结果尚未确认；"待处理资源操作"包括待发送及在途操作。

| 状态 | 含义 |
| --- | --- |
| `NONE` | 已确认不需要限制 |
| `CREATE_PENDING` | 停用请求已持久化，尚未发送或已发送但结果未确认，具体进度见操作记录 |
| `CREATE_FAILED` | 已确认本次创建失败（含紧急限制被明确拒绝），保存原因并进入调度待处理，不代表教室已被阻断 |
| `ACTIVE` | D 已确认该来源限制，是否已到生效时刻另按区间判断 |
| `RELEASE_PENDING` | 已确认恢复条件，解除请求待发送或正在核实/解除该来源，具体进度见操作记录 |
| `RELEASED` | 已确认解除，且不会被旧请求重新建立 |
| `CREATE_REJECTED` | D 明确拒绝本次计划限制，未建立资源限制 |

操作记录的执行状态建议为：`QUEUED`（已持久化、尚未发送）、`IN_FLIGHT`（调用中）、`RESULT_UNKNOWN`（已发送但无法确认结果）、`SUCCEEDED`（已确认成功）、`FAILED`（已确认失败）。`CREATE_PENDING`/`RELEASE_PENDING` 必须同时展示对应操作进度，不用于掩盖已经明确的失败。

解除被明确拒绝时，操作记为 `FAILED`，来源保留最后已确认状态并附解除失败原因，不显示已恢复；结果未知则继续 `RELEASE_PENDING`。同一来源尚有未确认创建时，不能只因另一次调用失败就宣称该来源不存在。未评估不能显示为 `NONE`；已拒绝的计划限制也不等于可以开工。多来源情况下逐条查询，不能只用一个布尔值表示整间教室是否可用。

### M3-R13 时间口径

全部判断以服务端时间和校园时区 `Asia/Shanghai` 为准，保存可明确转换的时间戳。停用采用左闭右开 `[stopFrom, stopTo)`，当且仅当 `start1 < end2 && start2 < end1` 时重叠。

报修、停用、维修和恢复时间精确到实际业务时刻，不按个人预约的整点或半点粒度取整；维修可跨日；安全停用不受 M1 的开放时间、时长、额度及本人取消截止约束。

须区分并分别保存：`discoveredAt`（实际发现时间）、`confirmedAt`（授权人员服务端确认时间）、`effectiveAt`（供预约取消与违约判断使用的可信业务生效时间）、`restrictionCreatedAt`（D 实际建立限制的时间）。默认 `effectiveAt = confirmedAt`，不能用后台处理或 D 响应返回时间覆盖它；第一版不接受普通客户端自行指定历史业务生效时间。

实际发现早于确认时，可记录发现时间与证据；是否追溯更正 `effectiveAt` 须由 M1/M3/D 共同确认规则及契约。启用后，只允许 `M3_RESOURCE_CONTROL` 授权人员凭依据发起更正，并经 D 保存版本/历史、通知 M1/M2 按各自规则核实更正；保留原值、操作者、理由与处理时间，不改写 D 当时实际建立限制的事实。该契约未确认前只保留发现记录，不自行回填业务生效时间或宣称下游更正完成。

### M3-R14 处理时限（建议基线）

> **配置说明**：以下时限为本稿建议值，按连续经过时长计算，不跳过夜间或周末，不是对真实物业响应能力的承诺。课程任务书未规定具体数字，请项目组确认后作为基线。

| 阶段 | `NORMAL` | `URGENT` | 计时起点 |
| --- | --- | --- | --- |
| 待评估 | 2 小时 | 15 分钟 | 工单创建时间 |
| 待派单 | 2 小时 | 15 分钟 | 评估完成时间 |
| 已派单待开始 | 4 小时 | 30 分钟 | 首次派单时间；计划施工以该时间与获准施工开始较晚者为准 |
| 维修 / 返修 | 24 小时 | 4 小时 | 本轮实际开始或验收退回时刻 |
| 待验收 | 24 小时 | 2 小时 | 本轮提交完工时刻 |

达到 `now >= deadlineAt` 即满足超时条件。紧急停用本身须立即发起，不受上表派单时限约束；计划施工的处理时限也不授权超出获准区间继续施工。

本稿将待评估与待派单分段计时：普通工单两段建议时限合计为 4 小时，紧急工单合计为 30 分钟，需团队确认这一建议口径；这是超时判定阈值，不代表超时会自动派单或保证实际等待不超过该值。有效性评估与资源影响确认均完成后才记录 `assessmentCompletedAt` 并进入待派单计时；在此之前仍按待评估阶段追踪。两个阶段可同处 `SUBMITTED`，通过当前处理阶段区分；重复评估或调整不重置已确认的阶段起点。

### M3-R15 超时升级

后台任务正常运行时每 60 秒检查未终结工单，按"工单 + 阶段轮次 + 升级类型"幂等记录一次超时，并进入调度工作台的超时列表。首版升级指向被授权的调度管理人员，记录时间、当前负责人和原因，不依赖邮件/短信。

- 超时不自动取消工单、不自动验收、不释放停用，也不处罚报修人。
- 每次人工推进状态前核对上一阶段是否已超时，不能因任务延迟或改派抹去超时事实。
- 仅进度更新不重置截止；提升级别后截止只能保持或提前，不能通过降级延后已发生的超时。
- 待验收已通过但资源解除仍未确认时，保留恢复失败/超时记录并继续追踪，不得让恢复任务从后台扫描中消失。

## 六、资源停用与跨模块联动

先用两个例子建立直觉，再看规则：

- **换灯管（不影响安全）**：报修 → 评估为"不影响使用" → 派单维修 → 完工验收 → 工单完成。全程教室照常预约，预约页面仅显示一条维修提示。
- **电线冒火花（安全故障）**：报修 → 授权人员确认紧急停用 → 教室立即整室封闭、已有预约被系统取消且不记违约 → 维修 → 独立验收 → 授权人员确认安全恢复 → 解除封闭；已取消的预约不自动恢复。

### M3-R16 普通维修提示

`NOTICE_ONLY` 只向统一资源查询提供脱敏提示，不建立阻断限制，不取消既有 M1/M2 预约，不阻止新申请和占用。普通工单完成后撤销本工单提示，其他来源提示继续保留。

### M3-R17 计划施工

当前可安全使用、未来施工才需停用的，授权人员提交 `stopFrom < stopTo` 的未来整室区间，D 原子校验与已有 M1/M2 占用的冲突。

- 普通计划施工不得覆盖已确认预约；冲突时记录拒绝原因并调整时间，工单保留，不自动取消预约或换教室。
- D 确认计划限制后，该未来区间对 M1/M2 生效；施工开始前须再次核实当前有效版本。
- 改期同样经过原子冲突判断；未知结果时不并行创建另一个来源"重试"；撤回旧计划只解除旧来源。
- 计划结束时刻是已批准的施工窗口边界，不是实际验收结论。预期不能按期恢复时须提前重新申请时段，不能无冲突检查地延长。
- 已发现实际安全隐患时，立即转入 R18 紧急停用，不能因延期申请冲突继续开放。
- 计划限制自动到期与安全恢复确认的协调方式须纳入 D 契约；未明确该保证前，不开放计划施工的实际开工功能。
- P0 仅开放区间申请、冲突查询/拒绝及未开工计划的撤回；实际开工与改期在 P1 验收。对尚未生效且从未开工的计划，`M3_RESOURCE_CONTROL` 人员可确认撤回并请求 D 仅解除本计划来源；解除未确认时显示处理中，不能先显示撤回成功。已经生效或已经开工的限制不得借普通撤回绕过 R20 的安全恢复条件。
- 未开工计划撤回不自动取消工单。若仍需处理故障，重新评估并保留历史；若尚未派单、无需再停用或维修，确认全部来源关闭且无待处理资源操作后，可按 R11 取消/驳回。P0 仅开放上述计划申请与撤回，不开放计划开工、改期等 P1 操作，也不将其显示为已支持。

### M3-R18 紧急整室停用

授权人员确认必须立即停用时，记录教室、工单来源、公开原因、确认人和可信生效时刻，立即请求 D 建立整室紧急限制；不等待维修人员到场、工单进入维修中或 M1/M2 取消完成。

- 紧急限制可与已有预约重叠；D 先阻断新的占用，再可靠通知受影响的 M1/M2。
- 停用结束时间不确定时，采用开放结束的持续限制；预计完工时间不能成为自动放行时间，不能因到 22:00 或跨月自动恢复。
- 请求超时（结果未知）则保持在途状态，以固定来源核实和重试，优先展示同步异常，不承诺网络故障时限制已生效。
- D **明确拒绝**且确认本次未建立限制时，按 `CREATE_FAILED` 与操作 `FAILED` 记录原因、负责人和后续处置，进入调度工作台待处理，不无限期停留在途。经授权人员处理失败原因后再发起可追溯的重试/修正操作，关联原请求并继续使用本工单来源，不能靠新建工单或盲目重放被拒请求绕过权限；仍有原在途请求时先核实。待处理安全要求继续保留，未确认限制生效前不得开需停用的维修，也不能显示已封室。
- 紧急故障的线下处置遵循学校既有流程，本模块页面不能替代现场安全处置。

### M3-R19 M1 与 M2 的受影响预约

M3 不自行实现预约取消，只向 D 提供可信限制事实，由各业务模块处理：

1. M1 对重叠的有效个人预约进入 `SYSTEM_CANCELLED`，保留原计划、签到、被迫结束时刻和停用原因，释放剩余占用、重算额度，不计违约。
2. M2 对重叠的已批准整室预约进入 `SYSTEM_CANCELLED`，保留审批历史和原时段，释放对应来源的剩余占用。
3. （对 D）已建立占用但 M1/M2 本地仍在确认中的请求也须核对，不能漏掉在途创建，也不能让迟到的成功响应覆盖系统取消。
4. 停用通知晚到时仍传递历史生效区间：M1 按其需求的延迟更正规则处理误记违约与额度；有效违约先发生而停用后生效的，不追溯免责；停用在预约结束后生效的，不回改正常完成。
5. 解除停用后，已取消的预约不自动恢复，须重新预约或重新申请。

M3 只保存调用、来源和协调进度，不跨表修改预约，也不擅自承诺所有业务取消都已完成。

### M3-R20 验收后的恢复与关闭

停用工单须有独立技术验收通过，**以及** `M3_RESOURCE_CONTROL` 授权人员的安全恢复确认；同一人兼具权限且符合 R03 时可一次操作完成两项确认。维修人员"修好了"或报修人评分不能单独恢复。

- 恢复按工单下每个已建立的限制来源执行，记录实际安全恢复时刻、确认人、释放请求号和结果。D 只解除本来源；其他工单、M1/M2 占用和长期禁用继续决定可用性。不存在限制的正常工单无需调用"清空教室"。
- 派单前误停用的更正：由授权验收人员独立核实原判断和安全条件，资源管理人员确认恢复，清理确认后按 R11 取消/驳回；记录更正依据，不伪造维修过程。
- 仅在验收通过、全部本来源限制已确认解除或确实不存在、待发送创建已撤销且在途创建已被安全终止、普通提示已撤除后，工单进入 `COMPLETED`。恢复响应丢失时保持在途和待验收状态，以同源核实重试，不提前宣布完成；恢复成功后核对完成条件，不重复要求人工验收。解除明确失败按 5.3 保存最后确认状态并提示人工处理，不把失败当成仍未收到结果。
- 恢复与新的停用确认并发时按来源版本串行裁决，旧释放不能解除较新的限制。恢复中发现新隐患时先持久化停止完成的处理意图，由授权资源管理人员确认并请求新限制；结果未知时保持处理中并阻止工单完成。新限制确认后保留原验收及新隐患依据，开启返修轮次，状态回到 `IN_PROGRESS`；旧释放响应不得覆盖这一结果，返修开工仍须满足 R08。已完成后发现的新故障另建工单。

### M3-R21 多来源与重复乱序

同室多张工单分别拥有自己的限制来源，解除 A 不解除 B。通知至少带 `eventId`、工单/限制来源、版本、操作类型、可信生效区间和处理时间。

- 相同事件重复到达，不重复产生限制、业务取消、违约或评价。
- 解除通知先于建立通知到达时，按来源版本及历史区间核实，不能只查当前已解除就丢掉曾影响预约的停用事实。
- 旧建立请求在确认解除后重放，不得再次封室。

### M3-R22 部分失败与可恢复性

发起外部操作前，先在 M3 持久化来源、请求内容和待处理操作。

- D 成功而 M3 保存最终结果失败时，重启后按相同来源核对，不换工单号重复建立限制。
- 同源查询"暂未找到"不能证明原请求不会迟到成功；结束工单或撤回计划前，D 须提供关闭在途创建、清理已有来源且防止旧请求重建的保证（或经评审的等效协议）。结果未知则保持处理中，不写无依据的终态。
- 停用建立、M1/M2 取消协调、M3 恢复分别记录结果。D 限制已生效但某模块通知失败时，保持限制并重试，不为回滚业务通知而开放资源。
- 首版采用持久化操作记录和普通恢复任务，不建设独立补偿平台。

### 7.2 M3 与 D 最小能力契约

M3 需要 D 实际提供以下能力，但不应在 M3 内编写模拟的"生产替身"冒充已联调：

| 能力 | 必要约定 |
| --- | --- |
| 身份与范围 | 用户角色、可报修/可管理教室、维修资格和人员有效性 |

## 九、异常、一致性与工程质量

### M3-R23 操作与错误处理

创建、取消、评估、派单、开工、进度、完工、验收、影响确认、恢复和评价均由后端独立校验身份、归属、状态和规则；重复点击或并发竞争（派单 vs 取消、改派 vs 完工、验收通过 vs 退回、恢复 vs 新停用）只能形成一个合法结果。

D 调用须区分**尚未发送**、**调用中/结果未知**、**已确认失败**。已持久化但未发出的操作标为 `QUEUED`，保留执行任务并在页面显示待发送；已发送但无法确认结果的标为 `RESULT_UNKNOWN`，保持处理中并以固定来源核实；明确拒绝按 `FAILED` 与 5.3 的来源状态规则记录并人工跟进。不接受请求且确认未发送的依赖失败返回清晰错误，不伪装成待确认；已经受理为持久化待处理操作的返回 `202` 和操作进度，不能同时误报为未受理。不得退化为 M3 单独写表宣称资源已变。对未登录、无权限、非法时间、状态冲突和依赖失败提供可理解的提示，不泄露他人信息。

### M3-R24 后台任务与审计

正常运行时每 60 秒执行可重复任务：超时升级、待发送操作的执行、在途限制建立/解除的核实、未完成的提示撤销和回调确认。明确失败的安全操作在调度工作台持续可见，由授权人员处理后恢复执行，不通过无限重放被拒请求代替人工处置。任务可重启继续，恢复队列不只放内存；D 不可达时记录原因并重试，不死循环高频请求。

每次重要操作保留工单、操作人、原/新状态、原因、可信业务时间、处理时间和请求关联。不覆写验收退回、历史停用或超时事实；日志中不落凭证、完整 token，不把完整故障描述、评价加入公共时间轴。

## 十、首迭代范围与后续事项

### 10.1 第一迭代必须完成（P0）

1. 登录授权与角色门槛、报修表单、本人记录/详情、合法取消。
2. 评估、驳回、人工派单/改派、维修任务/进度/完工。
3. 独立验收、退回返修、完成后一次评价。
4. 处理时限与幂等超时升级，调度工作台可查询处理。
5. 普通维修提示、紧急整室停用、安全恢复与按来源解除；包含多工单来源隔离、基础版本校验、重复去重、旧请求不复活和旧释放不覆盖新限制。
6. 计划施工的区间申请、冲突拒绝及未开工计划撤回/同源清理；实际开工与改期在 P1，依赖 D 到期协调契约。P0 的限制创建、查询与撤回能力也必须完成契约评审后才开放，不假装联调完成。
7. 状态审计、幂等与失败恢复、迁移/种子、真实单元/接口测试；M1/M2 网络联动演示（联调具备后验收）。

### 10.2 暂缓到后续迭代（P1）

计划施工的实际开工、改期及异常延期的完整流程，批量调整多工单限制的高级操作，图片附件、消息推送、自动派单、备件/费用、单座位停用、全楼批量停用、满意度报表、复杂申诉流程、独立补偿平台、运维控制台。基础来源隔离、版本校验、去重和防复活属于 P0，不因“高级操作延期”而削减。

**P1 不得破坏 P0 正确性**；尤其不能为"自动放行"绕过 D 的按来源解除机制。

| M3-T52 | 实际发现早于授权确认，申请追溯更正生效时刻 | 四类时间分别保留；契约未启用时只记录发现，启用后授权更正须经 D 历史版本及 M1/M2 核实，不以 M3 单表回填冒充下游更正完成 |

**通过标准**：每项 P0 功能有对应的代码位置、接口/页面演示步骤和自动化测试编号；无法在首迭代实现的条目仍保留并明确状态、原因与依赖，不从需求中删除。

## 十二、实施顺序与给 AI 的说明

> 本节可连同整份 Markdown 一起交给 AI。AI 应先给出实施方案、拟修改文件与风险说明，再分批编码，不一次性大改仓库。

建议分批：**A** 身份与报修闭环（迁移、角色适配、报修/我的报修/取消）；**B** 派单维修验收评价（评估、派单/改派、进度、完工、验收、评价）；**C** 时限与后台任务（截止、超时升级、审计）；**D** 停用联动（普通提示、紧急停用、恢复，与 D/M1/M2 联调）；**E** 前端与交付（工作台页面、错误反馈、运行与测试说明）。

- 不自建另一套资源占用引擎，不直连其他模块业务表；接口未就绪时测试可用受控替身，生产模式不得返回"永远安全/永远停用成功"。
- 所有业务校验在后端完成；对每个 `M3-Rxx`/`M3-Fxx` 提供实现位置及对应测试，覆盖 T01～T53；T28/T29 中明确的 P1 部分及 T48 随计划施工功能验收，其余 P0 行为不能因场景编号混用而省略。
- 每批形成可审查的小提交；测试失败不得合并；跨模块契约、D 或 schema 变化须组内评审。
- 测试与运行说明使用仓库实际命令，不凭空编写"已通过"或"已部署"的结论。
